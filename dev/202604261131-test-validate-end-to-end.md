# vit test-validate: End-to-End Workflow Proven on AFI_ValidateInitInput
**Date:** 2026-04-26
**Status:** completed
**Scope:** vit test-validate full workflow, PRIVATE function bridging, dual-call verification

## What Was Done

Built and tested the complete `vit test-validate` workflow: translate → test-validate → build → run → verify C++ ≡ Fortran. First function through the pipeline: `AFI_ValidateInitInput` (6 error branches + happy path = 7 tests, all passing).

## Problems Solved During Implementation

### 1. PRIVATE Function Visibility

`AFI_ValidateInitInput` has `PRIVATE` default access in the `AirfoilInfo` module — it's only callable from within the module (`AFI_Init`). The Fortran bridge couldn't `USE` it.

**Fix:** `generate_public_patch()` creates a patched copy of `AirfoilInfo.f90` with `PUBLIC :: AFI_ValidateInitInput` inserted after the existing PUBLIC declarations. This patched source is compiled locally in the test directory, producing a local `.mod` file that overrides the production `.mod` for bridge compilation only. The production build is untouched.

### 2. Derived Type C Interop

`AFI_InitInputType` is a regular Fortran derived type (no `BIND(C)` attribute). The bridge can't declare it directly as a BIND(C) parameter.

**Fix:** Bridge receives the struct as `TYPE(C_PTR), VALUE`, then converts via `CALL C_F_POINTER(ptr, fortran_pointer)`. The C++ test passes `&input` (pointer to the C struct, which has identical memory layout under `-fdefault-real-8`). The bridge also USEs `AirfoilInfo_Types` explicitly to get the type definition (the module's `PRIVATE` default prevents re-export of USEd types).

### 3. CHARACTER Interop

Fortran `CHARACTER(*)` (assumed-length string) is not C-interoperable. The bridge can't pass `char*` directly to a `CHARACTER(*)` parameter.

**Fix:** Bridge declares a local `CHARACTER(8196) :: ErrMsg` buffer, passes it to the Fortran function, and only returns `ErrStat` (the integer) to C++. For test-validate purposes, we only need to compare ErrStat between C++ and Fortran — the error message content is not compared across the language boundary.

### 4. shared_files Config Lost by save_config

`vit.yaml`'s `shared_files` section was silently dropped every time VIT's `save_config()` ran (during `vit verify`, `vit integrate`, etc.) because `save_config` didn't serialize the field.

**Fix:** Added `shared_files` serialization to `config.py:save_config()`.

### 5. Dual vit_types.h Files

`translations/vit_types.h` (generated by `vit translate`) and `modules/aerodyn/src/vit_types.h` (used by production build) had different content — the translations version included newly-translated types, the production version only had integrated types. Include path order determined which was found first.

**Fix:** Added `AFI_InitInputType` to the production `vit_types.h` so both files have consistent content. Long-term fix needed: consolidate to one canonical location.

### 6. build_c_params Dropped Derived Type Parameters

`build_c_params()` silently dropped derived-type parameters when called without the `derived_types` registry (defaulting `is_c_compatible=False`). This produced a skeleton with `void AFI_ValidateInitInput(int* ErrStat, char* ErrMsg)` — missing the `InitInput` parameter entirely.

**Fix:** Pass `derived_types` to `build_c_params()` in the skeleton generator.

## Build Architecture

The test harness links against the **production build's prebuilt libraries** — no project rebuild needed:

```
translations/AirfoilInfo/
├── afi_validateinitinput.cpp        # C++ translation
├── afi_validateinitinput_test.cpp   # Test harness (7 tests)
├── afi_validateinitinput_bridge.f90 # BIND(C) bridge to Fortran
├── AirfoilInfo.f90                  # Patched source (function made PUBLIC)
└── Makefile                         # Builds against production .a files
```

Makefile compiles:
1. **Patched AirfoilInfo.f90** → `AirfoilInfo.o` + local `airfoilinfo.mod` (with function PUBLIC)
2. **Bridge** → `afi_validateinitinput_bridge.o` (uses local .mod)
3. **C++ test** → `afi_validateinitinput_test.o` (includes translation as .hpp)
4. **Links** all three against `libbasicaerolib.a`, `libnwtclibs.a`, etc.

Key flags: `-I. -I<build>/ftnmods -J.` ensures the local `.mod` (with PUBLIC function) is found before the production `.mod` (with PRIVATE).

## Workflow Summary

For validation functions, the complete VIT workflow is:

```
vit translate FuncName -f source.f90                    # Generate scaffold + prompt
# Write the C++ implementation
vit test-validate FuncName translation.cpp -f source.f90  # Generate tests + bridge + Makefile
# Write the test implementations (from the prompt)
vit test-validate FuncName translation.cpp -f source.f90 --run  # Build and run
vit integrate FuncName translation.cpp -f source.f90 --apply    # Integrate
verify_aerodyn_baselines.sh all                          # 16/16 baselines
```

No KGen extraction needed. The test-validate tests replace KGen for functions where the interesting verification is branch coverage, not floating-point precision.
