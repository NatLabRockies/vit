# Phase 2 Prep: Subroutine Support and Array-Valued Function Results
**Date:** 2026-03-18
**Status:** completed
**Scope:** VIT enhancements to support Phase 2 target functions (ColemanTransform, ColemanTransformInverse, identity, matinv3)

## Overview

Phase 2 targets 4 Functions.f90 functions that use fixed-size arrays and subroutines — patterns VIT didn't handle in Phase 1 (which only had scalar functions). Before executing Phase 2 (extraction/verification/integration), VIT needed code changes. This work adds subroutine support and array-valued function result handling.

## Target Function Analysis

| Function | Type | Signature pattern | Reachable? |
|----------|------|-------------------|-----------|
| `ColemanTransform` | SUBROUTINE | `rootMOOP(3)` IN, scalar OUTs | Yes — scenario 2 (IPC, Y_ControlMode=2) |
| `ColemanTransformInverse` | SUBROUTINE | scalar INs, `PitComIPC(3)` OUT | Yes — scenario 2 (IPC, unconditional within IPC body) |
| `identity` | FUNCTION | `INTEGER` IN, returns `A(n,n)` | Yes — scenario 1 (WE_Mode=2, EKF at ControllerBlocks.f90:454) |
| `matinv3` | FUNCTION | `A(3,3)` IN, returns `B(3,3)` | **No — dead code, zero call sites. Deferred.** |

### matinv3 is Dead Code

`matinv3` is defined in Functions.f90 but has zero call sites anywhere in ROSCO. Like `CPfunction`, it cannot be extracted or verified — there's no runtime state to capture. Deferred until a call site exists.

### Reachability Details

**ColemanTransform** (Controllers.f90:510-511): Called unconditionally within the IPC subroutine body. IPC runs when `IPC_ControlMode >= 1 OR Y_ControlMode == 2`. Scenario 2 in vit_sim.py sets `Y_ControlMode=2`, so both ColemanTransform calls are reached.

**ColemanTransformInverse** (Controllers.f90:561-562): Also unconditional within IPC. Initially thought to require `IPC_ControlMode >= 1 AND Y_ControlMode != 2` (which is inside a conditional at line 542), but the actual calls at 561-562 are OUTSIDE that conditional — they run every time IPC executes. So scenario 2 reaches them.

**identity** (ControllerBlocks.f90:454): Inside `WindSpeedEstimator` when `WE_Mode == 2 AND WE_Op > 0`. The DISCON.IN sets `WE_Mode = 2` (Extended Kalman Filter). `WE_Op` starts at 0 but transitions to 1 during the simulation. The standard sim (scenario 1) exercises this path — confirmed by the WSE warning message in the output.

## Two-Step Implementation

### Step 2A: Subroutine Support

**The bug:** `build_c_params()` in `interface_gen.py` passed all scalar args by value. For subroutines, scalar INTENT(OUT/INOUT) args must be pointers because the Fortran BIND(C) interface passes them by reference (no VALUE attribute). The C parameter list and the Fortran interface must agree.

**The fix:** One change in `build_c_params()` — check if the signature is a subroutine and the arg is INTENT(OUT/INOUT); if so, use pointer type instead of value type.

**What already worked:** The rest of the subroutine pipeline was already implemented but untested:
- `generate_cpp_wrapper()` already used void return for subroutines
- `generate_fortran_interface_block()` already emitted SUBROUTINE keyword
- `generate_fortran_wrapper()` already used CALL syntax
- `_build_interface_args()` already omitted VALUE for OUT/INOUT scalars
- `_build_wrapper_call_args()` already passed OUT/INOUT args by reference
- Fixed-size arrays (`is_assumed_shape=False`) already didn't get spurious `n_` size params

**Tests added (15):** Parser tests for fixed-size array args and scalar OUT args, `build_c_params` tests for pointer vs value semantics, interface and wrapper generation tests for subroutines. All using ColemanTransform/ColemanTransformInverse-style synthetic Fortran snippets.

### Step 2B: Array-Valued Function Results

**The problem:** Functions like `identity(n) RESULT(A)` where `A` is `DIMENSION(n, n)` return arrays. C can't return arrays by value. The calling convention must transform: the result array becomes an additional output pointer parameter, and the C function returns void.

**Parser extension (`fortran_parser.py`):**
- Added `result_is_array: bool` and `result_dims: Optional[str]` fields to `FortranSignature`
- When parsing the result variable declaration, capture `is_array` and `dims` alongside `result_type`
- For `identity`: `result_is_array=True`, `result_dims="N, N"`, `result_type="REAL(DbKi)"`

**Interface generation changes (`interface_gen.py`):**

The key design decision: the **Fortran wrapper** remains a FUNCTION (so it's a drop-in replacement for the original), but the **C binding** is a SUBROUTINE (void return + output pointer for result). This means:

1. `build_c_params()`: When `sig.result_is_array`, append `(ret_type*, "<name>_result")` to the param list
2. `generate_cpp_wrapper()`: Array-result functions fall through to the subroutine path (void + all params including result pointer)
3. `generate_fortran_interface_block()`: Array-result functions emit SUBROUTINE (not FUNCTION) with the result as an INTENT(OUT) assumed-size `(*)` parameter
4. `generate_fortran_wrapper()`: Keeps FUNCTION header with RESULT clause, declares result with DIMENSION, then does `CALL <c_func>(args..., result_var)` instead of `result_var = <c_func>(args...)`
5. `_build_interface_args()`: Appends result as INTENT(OUT) assumed-size parameter
6. `_build_wrapper_call_args()`: Appends result variable name to call args

**Integration code (`integrate.py`):** `_generate_standalone_cpp()` uses the same `build_c_params()` and mirrors the function/subroutine branching — array-result functions now fall through to the void path.

**translate.py:** Uses `build_c_params()` for scaffold generation — automatically produces the correct void + output pointer signature after the interface_gen changes.

**Tests added (11):** Parser tests for result array detection, `build_c_params` tests for result pointer param, interface block tests confirming SUBROUTINE emission, wrapper tests confirming FUNCTION-wrapping-CALL pattern, regression test confirming scalar functions aren't affected.
