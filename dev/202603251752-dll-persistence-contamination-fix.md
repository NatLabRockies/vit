# DLL Persistence Source Contamination Bug and Fix
**Date:** 2026-03-25
**Status:** completed (contamination fix); in-progress (full re-extraction blocked)
**Scope:** VIT extraction, dll_persistence build wrapper, DISCON.F90 contamination

## Background

VIT's `dll_persistence` mechanism (configured in `vit.yaml`) inserts Fortran code via `sed` into the project source during KGen extraction. This works around a real issue where Python's `ctypes.CDLL` doesn't truly unload Fortran shared libraries on `dlclose()` — SAVE variables persist across "reloads," causing KGen's invocation counters and ROSCO's initialization guards to carry stale state into the state capture phase.

Two patches are inserted:
1. **Project-specific reset**: `LocalVar%AlreadyInitialized = 0` before `CALL ReadAvrSWAP` — forces ROSCO to re-run `SetParameters` even if the DLL wasn't truly unloaded
2. **KGen-generic reset**: `DEALLOCATE(kgen_isstop, ...)` before KGen's allocation check — resets KGen's invocation counters

Both are necessary: without #1, `SetParameters` doesn't run and CntrPar has stale data → 0 state files. Without #2, KGen's invocation counter starts at >20 (from profiling phase) → 0 state files within the 0:0:1-20 capture range.

## The Bug

### Discovery

While attempting to re-extract all 28 golden kernel fixtures (needed after the avrSWAP size fix from dev note `202603251411`), 14 of 28 extractions produced 0 state files. Investigation revealed that `rosco/controller/src/DISCON.F90` had accumulated **24 copies** of `LocalVar%AlreadyInitialized = 0` at lines 81-104 — one per previous extraction. This shifted all subsequent line numbers by +24, causing KGen to insert instrumentation pragmas at the wrong locations for DISCON.F90-targeted extractions.

### Root Cause

The build wrapper script (`.vit_build_wrapper.sh`, generated by `extract.py:generate_state_capture_build_script()`) applies `sed` patches to ALL `.f90`/`.F90` files in the source directory:

```bash
for f90 in "${source_dir}"/*.f90 "${source_dir}"/*.F90; do
    sed -i '/CALL ReadAvrSWAP/i\    LocalVar%AlreadyInitialized = 0' "$f90"
done
```

KGen's Makefile has a save/replace/build/recover workflow:
1. `save` — backs up files KGen will instrument to `.kgen_org`
2. `replace` — copies KGen-instrumented files over originals
3. Build wrapper runs (our sed patches + compile + install)
4. `mv .kgen_org` — restores KGen-instrumented files from backup

KGen only backs up files it instruments. For a `Controllers.f90` extraction, KGen instruments Controllers.f90, Constants.f90, ROSCO_Types.f90, etc. — but **NOT DISCON.F90**. So DISCON.F90 has no `.kgen_org` backup and is never restored. The sed insertion persists.

### Why it wasn't caught during the build wrapper

The build wrapper script starts with `set -e` (exit on any error). The build command (`cmake --build .`) is executed directly — if it returns nonzero for any reason (e.g., a warning treated as error, a transient filesystem issue), `set -e` causes the script to exit immediately, **skipping all subsequent cleanup code**. Even when the build succeeds, the cleanup step was never reached because `set -e` was also triggered by other commands in the pipeline.

## The Fix

### Approach: Tagged Insertions

Instead of backing up and restoring files (which proved fragile due to timing issues with `.kgen_org` existence, `set -e`, and the build wrapper running twice per extraction), all sed-inserted lines are tagged with a Fortran comment `!VIT_DLL_RESET`. After the build completes (the compiled library already has the patches baked in), a cleanup step removes all tagged lines from the source:

```bash
# INSERT phase (before build):
sed -i '/CALL ReadAvrSWAP/i\    LocalVar%AlreadyInitialized = 0 !VIT_DLL_RESET' "$f90"

# CLEANUP phase (after build):
sed -i '/!VIT_DLL_RESET/d' "$f90"
```

Why this works:
- `!VIT_DLL_RESET` is a Fortran comment — doesn't affect compilation
- The tag is unique — won't match real code
- Removal by tag is idempotent — safe to run multiple times
- No backup files, no `.kgen_org` timing issues, no variable tracking

### `set -e` Fix

The build command is now wrapped in `set +e` / `set -e` so the cleanup step always runs regardless of build outcome:

```bash
set +e
${build_cmd}
BUILD_RC=$?
set -e
# ... install ...
# ... cleanup (tagged line removal) ...
exit $BUILD_RC
```

### Files Changed

- `vit/vit/extract.py`:
  - Tagged all dll_persistence sed insertions with `!VIT_DLL_RESET`
  - Added Step 5 cleanup: removes `!VIT_DLL_RESET` tagged lines after build
  - Added `set +e` around build command, `|| true` on install

### Verification

Three sequential extractions (saturate → wrap_180 → LPFilter) with `grep -c AlreadyInitialized DISCON.F90` after each:
- Before fix: 0, 1, 2 (contamination accumulating)
- After fix: 0, 0, 0 (clean)

## Failed Approaches

### Attempt 1: Backup/restore based on `.kgen_org` existence
Back up files without `.kgen_org` before sed, restore after build. Failed because:
- `.kgen_org` existence changes between elapsedtime and state capture phases
- The check happened inside the build wrapper which runs for both phases
- Timing: whether `.kgen_org` exists at the check depends on which KGen phase is running

### Attempt 2: Only sed files with `.kgen_org`
Skip sed for files KGen didn't back up. Failed because:
- DISCON.F90 (which needs the `AlreadyInitialized` reset) has no `.kgen_org` when the target is in Controllers.f90
- Skipping the sed for DISCON.F90 means the reset never applies → 0 state files

### Attempt 3: Backup all, restore non-KGen files
Back up all files, restore those without `.kgen_org` after build. Failed because:
- `set -e` caused the script to exit before the restore step executed
- The restore code was structurally correct but never ran

## Status of Full Re-extraction

The contamination fix is verified. However, full re-extraction of all 28 kernels is **blocked** by a separate issue: Filters.f90-targeted extractions (wrap_180, LPFilter, HPFilter, SecLPFilter, NotchFilter, NotchFilterSlopes) produce 0 state files even with clean source. This appears to be a KGen invocation ordering issue — these functions may not be reached within the 0:0:1-20 capture range depending on which scenario runs first in `vit_sim.py`. This is a pre-existing issue (the previous golden fixtures were extracted at a time when it worked, possibly with different scenario ordering or extraction parameters). Investigation pending.

Functions that extract successfully with 20 state files: saturate, ratelimit, interp1d, PIController, IPC, ForeAftDamping, FloatingFeedback, ActiveWakeControl, SecLPFilter_Vel, VariableSpeedControl, CableControl, StructuralControl, PitchControl (with correct line numbers).

## Corrections to Previous Dev Notes

### 202603250848 (CableControl Heap Crash)
**Status update: superseded.** The heap crash (`malloc(): unaligned tcache chunk detected`) was attributed to VIT's field logging causing excessive heap churn. The actual root cause was the **avrSWAP heap overflow** — writing to avrSWAP(2601) with a 2000-element allocation corrupted the heap. With avrSWAP=3000, CableControl passes 40/40 with field logging enabled and no crash. The SAVE/reuse patches (commit `6366400`, reverted at `071b03d`) were unnecessary — the fix was the correct avrSWAP size.

### 202603251133 (WE_FOPoles State File Data Error)
**Status update: resolved.** The WE_FOPoles entry=0.0 was not a KGen state file bug, DLL persistence issue, or binary format misalignment. It was the **avrSWAP heap overflow** — CableControl writing to avrSWAP(2601) overwrote WE_FOPoles(3) with 0.0 in the kernel's heap memory. The state file itself was correct (confirmed by binary parse). Similarly, StructuralControl's VS_KP (float32 truncation) and PC_GS_KI (small diff) were caused by avrSWAP(2801+) overflow corrupting different heap locations.
