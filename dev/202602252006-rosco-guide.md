**Date:** 2026-02-25

## Summary

Commits a3cd688 and 9920b9b (roughly 4 minutes apart) added `guide_ROSCO.md`, a 466-line comprehensive guide for using VIT with the ROSCO wind turbine controller codebase. This was written immediately after the first successful end-to-end run of VIT against ROSCO's `saturate` function, capturing the exact steps and commands that worked. The quick follow-up commit fixed a minor documentation issue in the guide.

## Background

By this point in the day (roughly 8:06 PM on February 25), VIT had gone from initial commit to working end-to-end pipeline in about 5 hours of intensive iteration. The five preceding commits had fixed type case preservation, KGen pragma format, the extraction pipeline, kernel compilation, and USE statement handling. The `saturate` function — a simple min/max clamp — had been successfully extracted, verified, and was ready for integration.

Writing the guide at this point served two purposes:

1. **Capture institutional knowledge** — The exact sequence of commands, environment setup, and workarounds needed to run VIT against ROSCO was only in the developer's head. Many steps had non-obvious ordering requirements (build before extraction, turbine model pickle before simulation, etc.).

2. **Define the reference workflow** — With so many moving parts (Docker container, Python 2.7 for KGen, Python 3 for VIT and ROSCO, CMake build system, shared library installation), having a canonical step-by-step workflow prevents wasted time on environment issues.

## What the Guide Covers

### Environment Setup

The guide documents the Docker container approach: all building, extraction, simulation, and testing happens inside a container named `vit-dev` that mounts the workspace. It specifies:

- The mount mapping (Mac path to container path)
- How to execute commands inside the container
- What's pre-installed (Ubuntu 24.04, gfortran, g++, cmake, Python 3.12, Python 2.7)
- How to rebuild Python 2.7 if the container is destroyed (from a pre-downloaded tarball, since the container has no network access due to corporate TLS inspection)

### ROSCO Build Process

Step-by-step instructions for building ROSCO's Fortran controller library (`libdiscon.so`), including the CMake invocation and the critical step of copying the built library to where ROSCO's Python simulation expects to find it.

### Turbine Model Initialization

A detail that's easy to miss: ROSCO's simulation script (`04_simple_sim.py`) loads a pickled turbine model that doesn't exist on a fresh clone. The guide documents running `01_turbine_model.py` first to generate this pickle file.

### The Full VIT Pipeline

Each of the three VIT stages (extract, verify, integrate) is documented with exact commands, expected output, and explanations of the flag semantics. Notably, it clarifies a confusing aspect of the CLI: the `--file` flag means different things for different commands:

- For `extract`: the file containing the **call site** (Controllers.f90)
- For `verify` and `integrate`: the file containing the function **definition** (Functions.f90)

### Baseline Capture and Diff Verification

The guide describes how to capture baseline simulation output before integration and diff it against post-integration output to confirm byte-identical behavior. This is the ultimate end-to-end test — not just that the C++ function produces the same outputs for captured inputs, but that the entire simulation produces identical results when the C++ replaces the Fortran.

### vit.yaml Configuration

Annotated explanation of every field in the configuration file, including the KGen-specific settings (invocation format, build/run/clean commands) and Fortran-specific settings (kind aliases, compiler).

## Significance

This guide later evolved into the `CLAUDE.md` project instructions file, which serves as the canonical reference for the entire workspace. Many of the sections in `CLAUDE.md` — the workflow steps, configuration documentation, environment setup, and testing procedures — trace their lineage directly to this original guide.

The guide also established the practice of documenting exact commands with expected output, which proved invaluable during later development when changes to VIT's internals needed to be validated against the known-good workflow. Having the "golden path" documented meant any regression was immediately obvious: if the commands in the guide stopped working, something was broken.

## Broader Context

Writing comprehensive documentation on the same day as the initial implementation was a deliberate choice. VIT's architecture involves multiple tools (VIT itself, KGen, ROSCO, CMake, Docker), multiple languages (Python 3, Python 2.7, Fortran, C++), and multiple environments (Mac host, Linux container). The surface area for "it works on my machine" problems is enormous. The guide reduces this risk by making the exact working configuration explicit and reproducible.
