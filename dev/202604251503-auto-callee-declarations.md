# Automated Callee Declarations Across All VIT Contexts
**Date:** 2026-04-25
**Status:** completed
**Scope:** VIT infrastructure — translate, verify, integrate

## Problem

When a C++ translation calls another already-translated function (e.g., `ComputeUA360_updateCnSeparated` calls `computeua360_cnoffset_c`), the callee's `_c` declaration must be available at compile time. Previously this was handled inconsistently:

- **Kernel verification:** Automated. VIT generates `vit_kernel_callees.h` during `vit verify` with per-function callee declarations. The kernel wrapper `.cpp` auto-includes it.
- **Production integration:** Manual. VIT creates `vit_translated.h` with all `_c` declarations, but the generated production `.cpp` did NOT include it. Translators had to add inline `extern "C" { }` blocks manually.
- **Translation prompt:** Silent. `vit translate` did not mention callees at all — the translator had no way to know what `_c` functions were available or their signatures.

This worked for ROSCO because translators manually wrote the declarations (guided by looking at other translations), but it was error-prone and would not scale.

## Root Cause

`_generate_standalone_cpp()` in `integrate.py` generated the production `.cpp` wrapper with `#include "vit_types.h"` but never included `vit_translated.h`. The header existed (created by `_apply_header_patch` during each `vit integrate --apply`) but was orphaned — nothing included it.

## Fix: Three Changes

### 1. Production `.cpp` auto-includes `vit_translated.h` (integrate.py)

`_generate_standalone_cpp()` now emits `#include "vit_translated.h"` after the struct headers. This is unconditional — every production wrapper includes it, whether or not the function has callees. Harmless when empty (the header has an include guard), correct when populated.

Also made `vit_translated.h` self-contained by adding `#include "vit_types.h"` to the generated header guard block, so struct types used in callee declarations (like `afi_table_type_view_t*`) are always resolved.

**Commit:** `1483b72`

### 2. `vit translate` shows callee `_c` signatures in the prompt (cli.py, translate.py)

`cmd_translate` now:
1. Extracts the target function's Fortran source
2. Calls `detect_callees()` (from `kernel_verify.py`) to find all function calls
3. Filters to those present in `config.translations` (already integrated)
4. For each, finds the callee's signature and generates its `_c` declaration via `_generate_c_declaration()`
5. Passes the declarations to `generate_translation_prompt()`

The prompt now includes an "Already-Translated Callees" section:

```
## Already-Translated Callees

This function calls the following already-translated functions. Call them
directly using these C signatures — the declarations are provided
automatically by VIT (do NOT add your own `extern "C"` or `#include`
for these).

```c
double computeua360_cnoffset_c(afi_table_type_view_t* p, double* cn_cl, int n_cn_cl, int Row, int iLower);
```
```

The explicit instruction not to add manual declarations is important — it prevents the old pattern of inline `extern "C"` blocks that can conflict with VIT's auto-generated headers.

**Requirement:** Must be run on clean (pre-integration) source. The callee detection parses the original Fortran function body; if the function is already integrated, the wrapper body has no CALL statements to detect.

**Commit:** `e82213e`

### 3. Kernel verification already handled (existing)

`_generate_callee_bridges()` in `kernel_verify.py` auto-generates `vit_kernel_callees.h` during `vit verify`. The kernel wrapper `.cpp` auto-includes it. No changes needed here.

## The Full Chain

| Context | Header | Generated by | Included by |
|---------|--------|-------------|-------------|
| Translation prompt | (inline in prompt text) | `cmd_translate` in cli.py | (shown to translator) |
| Kernel verification | `vit_kernel_callees.h` | `_generate_callee_bridges` in kernel_verify.py | kernel wrapper .cpp (auto) |
| Production build | `vit_translated.h` | `_apply_header_patch` in integrate.py | production wrapper .cpp (auto, new) |

All three contexts now handle callee declarations automatically. Translators write pure implementation code — no `extern "C"`, no `#include "vit_translated.h"`, no manual signature lookups.

## Impact

- Eliminates a class of integration errors (wrong callee signatures, missing declarations)
- Translation files are simpler — just the algorithm, no boilerplate
- Scales to AeroDyn's 507 functions where manual declaration management would be impractical
- Retroactively explains why ROSCO's inline `extern "C"` blocks worked but were fragile
