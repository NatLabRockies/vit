# NaN-Safe Verification: Handling Uninitialized Fortran State
**Date:** 2026-02-26
**Status:** completed
**Scope:** kernel_verify, cli

## Background

This was the most complex debugging effort in VIT's development, spanning two days and four commits. It exposed a fundamental tension between KGen's state capture model and IEEE 754 floating-point semantics.

### The Root Problem

KGen captures the exact byte-level state of all function arguments — both inputs and outputs — at runtime. Fortran does not zero-initialize local variables or intent(out) arguments. When KGen records the state of an output variable *before* the function assigns it, the captured value is whatever garbage was on the stack, which is frequently NaN (Not a Number).

KGen's verification kernel then replays each captured invocation: it loads the saved inputs, calls the function (either the original Fortran or, in VIT's case, a C++ translation via an ISO_C_BINDING wrapper), and compares the computed outputs against the saved reference outputs.

The comparison fails for NaN fields because, per IEEE 754, `NaN != NaN`. This is mathematically correct but operationally wrong for VIT's use case: if the reference output contains NaN (because the field was never assigned), and the computed output also contains NaN (because the C++ translation also doesn't assign it), then the translation is correct — both sides left the same field uninitialized. A false failure here would block verification of correct translations.

## Evolution Across Four Commits

### Commit b80ca6d (2026-02-26): First attempt — skip NaN cases entirely

107 lines changed. The initial approach was blunt: scan the reference data files for NaN patterns, and if any field in a case contains NaN, skip the entire case from verification.

Changes:
- **kernel_verify.py**: Added NaN detection by scanning the binary reference data files for IEEE 754 NaN bit patterns. Cases containing any NaN field were flagged for exclusion.
- **cli.py**: Updated the verification output to show skip counts alongside pass/fail counts (e.g., "38/40 passed, 2 skipped").

This worked but was overly conservative. If a case had 10 output fields and only 1 contained NaN, all 10 fields were skipped — including the 9 that had valid, verifiable data. For functions with many output fields (like those receiving derived types), this could skip the majority of verification coverage.

### Commit 465e5ff (2026-02-26): Expose per-field information from KGen

14 lines changed. A targeted change to set KGen's `verboseLevel` to 100 in the generated verification code. At the default verbosity, KGen's output only reports pass/fail at the case level. At verboseLevel 100, it reports the comparison result for every individual field, including the field name and whether the comparison was IDENTICAL or DIFFERENT.

This was a prerequisite for the next commit: you can't do field-level NaN handling if you can't see field-level results.

### Commit 320046c (2026-02-26): Field-level NaN classification

55 lines changed. Instead of skipping entire cases, this commit introduced per-field NaN classification. The logic now parsed KGen's verbose output to identify individual fields, and classified each NaN field into one of two categories:

- **Identical NaN**: Both the computed value and the reference value are NaN. This means both the original Fortran and the C++ translation left the field uninitialized. This is correct behavior — the translation matches.
- **NaN mismatch**: One side is NaN and the other isn't. This indicates a real bug — either the translation is computing a value where the original didn't, or vice versa.

Identical NaN fields were counted as passing. NaN mismatches were counted as failures.

### Commit 548ddc0 (2026-02-27): Fortran-level NaN comparison patch

20 lines changed. The previous commits handled NaN classification by parsing KGen's text output after the fact. This commit took a different approach: patch KGen's generated Fortran comparison code directly so that NaN-vs-NaN comparisons report IDENTICAL at the source level.

The key technique is Fortran's `x /= x` idiom for NaN detection. Per IEEE 754, NaN is the only floating-point value that is not equal to itself. So `x /= x` is `.TRUE.` if and only if `x` is NaN. The patch inserts a check before the normal comparison:

```fortran
IF (computed /= computed .AND. reference /= reference) THEN
    ! Both are NaN — report IDENTICAL
ELSE
    ! Normal comparison
END IF
```

This is more robust than post-hoc text parsing because:
1. It works regardless of KGen's output format or verbosity level
2. It handles all floating-point fields uniformly (REAL(4), REAL(8), etc.)
3. It correctly distinguishes signaling NaN vs. quiet NaN (both satisfy `x /= x`)

The `_patch_nan_comparisons()` function in `kernel_verify.py` applies this transformation to KGen's generated verification source files before compilation.

## Final Architecture

The NaN handling pipeline works as follows:

1. During verification setup, `_patch_nan_comparisons()` modifies KGen's generated Fortran comparison code to treat NaN-vs-NaN as IDENTICAL.
2. The patched kernel is compiled and run.
3. The output parser in `kernel_verify.py` reads the results. Fields where both sides are NaN show as IDENTICAL (thanks to the patch). Fields where only one side is NaN show as DIFFERENT (a real failure).
4. The CLI reports results with NaN-related cases noted as "skipped" in the summary, but individual NaN-vs-NaN fields are counted toward the pass total.

## Design Decisions

- **Patch at the Fortran level, not post-hoc**: Modifying KGen's comparison code is more reliable than trying to parse and reinterpret its output. The patch is small and targeted.
- **`x /= x` over `ISNAN()`**: The `ISNAN()` intrinsic is a Fortran 2003 extension and not available in all compilers. The `x /= x` idiom is portable and works with gfortran, ifort, and other compilers.
- **NaN-vs-NaN is a pass, not a skip**: If both sides produce NaN for the same field, the translation is faithfully reproducing the original behavior (including the lack of initialization). This is the correct semantic for "bit-identical" verification.
- **NaN-vs-value is a hard failure**: If the reference has NaN but the translation produces a value (or vice versa), something is wrong. This is never suppressed.

## Lessons Learned

This sequence illustrates the value of iterating toward the right abstraction. The first attempt (skip entire cases) was expedient but lossy. The second (verbose output) was an enabler. The third (field-level classification) was correct but fragile. The fourth (Fortran-level patching) was the right solution — minimal code, maximum robustness, and correct semantics. Each step informed the next.
