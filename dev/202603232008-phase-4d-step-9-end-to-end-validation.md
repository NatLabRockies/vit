**Date:** 2026-03-23

**Scope:** Phase 4D final validation — first ControlParameters view type function through the full pipeline

## Planning

### Target Selection

ForeAftDamping was chosen as the simplest ControlParameters function:
- 21 lines of Fortran
- 3 args: CntrPar (view type), LocalVar (BIND(C)), objInst (BIND(C))
- Only calls PIController (already translated 40/40)
- Read-only CntrPar access (FA_KI, FA_IntSat scalars)
- Call site: Controllers.f90 line 80, gated by `CntrPar%TD_Mode > 0`

### Pre-requisite: TD_Mode

ForeAftDamping is gated by `TD_Mode > 0`. All ROSCO scenarios had `TD_Mode=0`. Added `'TD_Mode': 1` to vit_sim.py Scenario 3's parameter patches. ForeAftDamping reads `FA_AccHPF` (which is 0.0 in the 1-DOF sim) and produces 0.0 output — fine for verifying the view type mechanism.

### Expected Validation Chain

1. Extract: KGen captures 20 state files
2. Verify: VIT generates view struct header + populator + callee bridge, kernel builds and runs 40/40
3. Integrate: populator .f90 + C++ wrapper + CMake SOURCES
4. Rebuild + diff: byte-identical simulation output

## Implementation

### C++ Translation

ForeAftDamping calls PIController. The initial translation used `#include "vit_translated.h"` for the `picontroller_c` declaration. This works in integration context but not in the kernel, where the shared header doesn't exist.

The translation was rewritten to declare `picontroller_c` via `extern "C"` locally. In the kernel, the callee bridge (generated by VIT) provides this entry point. In integration, the shared header provides it.

### Extraction

Successful on first attempt: `Extraction successful, Cases: 20`. KGen instrumentation and simulation worked correctly with TD_Mode=1.

## Debugging: Five Sequential Failures

Step 9 required solving five distinct build failures, each revealing a gap in the infrastructure.

### Failure 1: Missing nested type headers

```
localvariables_t.h:175:5: error: 'rlparams_t' does not name a type
```

**Root cause:** `build_derived_type_registry()` only discovered types from function arguments. LocalVariables has nested `TYPE(piParams)`, `TYPE(FilterParameters)`, `TYPE(WE)`, `TYPE(rlParams)`, `TYPE(resParams)` — five nested types that the registry never found.

**Fix:** Added fixed-point expansion loop to `build_derived_type_registry()`. After the initial argument scan, iterates through all registered types' fields looking for `TYPE(X)` references. Adds newly-discovered types to the registry. Repeats until no new types found. A `visited` set guards against circular references and re-querying.

Result: 8 types discovered (was 3). LocalVariables' 5 nested types plus their transitive dependencies.

### Failure 2: Undefined reference to `picontroller_c`

```
/usr/bin/ld: foreaftdamping_cpp.o: undefined reference to `picontroller_c'
```

**Root cause:** ForeAftDamping's C++ calls `picontroller_c()`, but in the kernel, PIController is still Fortran with no C entry point. No callee bridge existed.

**Fix:** Designed and implemented the kernel callee bridge subsystem:
- `detect_translated_callees()` — scans original source for callees, cross-references against `vit.yaml` translations
- `generate_kernel_callee_bridge()` — generates Fortran BIND(C) bridge that wraps C→Fortran (inverse of integration wrapper)
- `generate_callee_declarations_header()` — C header with `extern "C"` declarations
- `_generate_callee_bridges()` — orchestration in `setup_kernel_cpp()`
- `_add_bridges_to_makefile()` — Makefile integration

### Failure 3: Callee detection found nothing

```
Detected callees: []
```

**Root cause:** `_generate_callee_bridges()` searched the PATCHED kernel source for callees. But the kernel's Controllers.f90 had ForeAftDamping's body already replaced with the C-calling wrapper — the original `PIController(...)` call was gone.

**Fix:** Changed to read the ORIGINAL source file (from `sig.source_file`) instead of the patched kernel. The callee detection must run against the pre-patched code where the original function body still exists.

### Failure 4: Bridge can't find PIController

```
Fatal Error: Cannot open module file 'controllers.mod' for reading
```

**Root cause:** The bridge BIND(C) function had `USE Controllers, ONLY: PIController` but compiled before Controllers.o. The Makefile dependency only listed `ROSCO_Types.o`.

**Fix:** Changed `_add_bridges_to_makefile()` to depend on ALL existing Fortran .o files (excluding the bridge itself and C++ .o). The bridge is a leaf node — nothing depends on it except the linker — so broad dependencies are safe. This ensures all module .mod files are available before the bridge compiles.

Also fixed: populator dependency was PREPENDED to the Controllers.o rule, making it the first prerequisite. Make's `$<` expands to the first prerequisite, so `Controllers.o: vit_controlparameters_view.o Controllers.f90 ...` tried to compile `vit_controlparameters_view.o` as Fortran source. Changed to APPEND dependencies so the `.f90` source remains first.

### Failure 5: LOGICAL type mismatch + INOUT conversion error

```
Error: Type mismatch in argument 'reset' at (1); passed LOGICAL(1) to LOGICAL(4)
Error: Non-variable expression in variable definition context (actual argument to INTENT = OUT/INOUT)
```

**Root cause (LOGICAL):** The bridge declared `reset` as `LOGICAL(C_BOOL)` (1-byte) via the BIND(C) interface, but PIController expects `LOGICAL` (4-byte). No conversion was applied.

**Root cause (INOUT):** The bridge wrapped ALL scalar args in conversion functions (`INT(inst, 4)`), creating temporaries. Fortran can't pass temporaries to INTENT(INOUT) arguments — they're not addressable variables.

**Fix:** Updated `_build_bridge_call_args()`:
- INTENT(INOUT/OUT) args: pass directly (no wrapping — gfortran handles implicit kind promotion for by-reference args)
- LOGICAL args: explicit `LOGICAL(arg)` conversion
- Other VALUE scalars: pass directly (BIND(C) VALUE types are compatible with Fortran implicit conversion)

## Reflection

### Step 9 is the test that matters

501 passing tests, three successful reflection cycles, and structural correctness verified by field-by-field comparison. None of that caught the five failures that surfaced when we actually ran the pipeline on a real function. Unit tests verify components; end-to-end tests verify systems. The failures were all at system boundaries — between the registry and kernel_verify, between the callee bridge and Makefile semantics, between BIND(C) type conventions and original Fortran signatures. These are the seams that component tests can't reach.

### Build system integration is where the bugs hide

The view struct layout was correct. The populator was correct. The bridge logic was correct. Every failure was in Makefile dependencies, module visibility, compilation ordering, or type conversion at the C/Fortran boundary. These depend on gfortran's module semantics, Make's dependency resolution, and BIND(C) type conversion rules — the least testable parts of the system. The only way to test them is to actually build.

### The iterative debugging loop works

Five failures in sequence sounds bad, but each was identified precisely by the compiler or linker error, fixed with a targeted change, and verified immediately. Total debugging time was less than planning time. The real cost was extraction time (~2 minutes per attempt, 6 extractions total). If extraction were faster, the iteration cycle would be much tighter.

### What this means for Phase 7B

The callee bridge system means Phase 7B translations can call any already-translated function (saturate, PIController, interp1d, all filter functions) through the `_c` entry points, even in kernel verification. No inlining needed. The nested type registry handles arbitrarily deep type hierarchies. The view struct gives C++ access to all 68 ALLOCATABLE fields in ControlParameters. The infrastructure is ready.
