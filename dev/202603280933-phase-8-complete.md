# Phase 8 Complete: All ControllerBlocks.f90 Functions Translated
**Date:** 2026-03-28
**Status:** completed
**Scope:** Phase 8 — ControllerBlocks.f90 module translation, 2D array VIT infrastructure, verification regression fix

## Plan

Phase 8 targeted all functions in ControllerBlocks.f90, the largest untranslated module in ROSCO. The original PROJECT_PLAN listed 8 functions, but investigation revealed 9 (PitchSaturation was missing) plus 2 Functions.f90 dependencies (interp2d, AeroDynTorque) needed for WindSpeedEstimator. The plan also incorrectly stated matinv3 was needed — source inspection confirmed WindSpeedEstimator's Kalman filter uses a 1×1 innovation covariance S, so "inversion" is just scalar division. matinv3 is dead code in ROSCO.

The plan was structured into three tiers:
- **Tier 1 (8A):** PitchSaturation — simple function, unblocks PitchControl integration (27→29)
- **Tier 2 (8B):** 7 remaining ControllerBlocks functions — 4 using Scenario 3, 3 needing new Scenario 9
- **Tier 3 (8C):** WindSpeedEstimator + interp2d + AeroDynTorque — requires VIT 2D array infrastructure

## Process and Issues

### Tier 1 (8A): PitchSaturation + PitchControl Unblock

PitchSaturation was straightforward — 28 lines, calls interp1d + max. Extracted from Controllers.f90:87 (inside PitchControl), Scenario 3. Verified 21/21 on first attempt. Integrated PitchSaturation, then integrated PitchControl (which had been verified since Phase 7B but blocked on the missing `pitchsaturation_c` symbol). Integration test: 29/29, 612,000 values ALL IDENTICAL.

**Issue: Verification regression completely broken.** After the integration test, running `verify_all.sh` produced 23/29 failures with "no cases found". This consumed significant debugging time. Five wrong hypotheses were investigated before finding the root cause:

1. ~~Parallel race condition on kgen_statefile.lst~~ — each function has its own kernel dir, no shared state
2. ~~Zombie verify process from killed run~~ — found and killed one, but failures persisted
3. ~~Colima FS mount latency~~ — real contributing factor but not root cause
4. ~~Stale build artifacts~~ — cleanup helped but didn't fix the deterministic failures
5. ~~Cleanup script deleting tracked golden fixture files~~ — real bug (git not installed in container, silent failure), but still not root cause

**Actual root cause:** `vit verify` scans the ROSCO source directory to detect translated callees and generate callee bridges. When the source was in the **integrated** state (with `_c()` wrappers from the integration test), callee detection failed — the function signatures were wrapped and didn't match. Functions without callees (saturate, wrap_180, identity) passed; functions with callee bridges (ForeAftDamping→PIController, PitchControl→PitchSaturation) all failed.

**Fix:** Run `reset_to_clean.sh` before verification. Added a source state check to `verify_all.sh` that detects `_c(` in Controllers.f90 and exits with a clear error. Also added build artifact cleanup (`.o`/`.mod`/`.exe`/`.csv`).

**verify_all.sh rewrite:** Replaced the `-j N` parallel approach (which caused issues with Colima FS timing and zombie processes) with batch mode. The script accepts `1`, `2`, or `3` to run specific batches, enabling parallel execution via three separate `docker exec` calls.

### Tier 2 (8B): Seven ControllerBlocks Functions

**Scenario 3 functions (4):** StateMachine, SetpointSmoother, PowerControlSetpoints, ComputeVariablesSetpoints. All extracted from DISCON.F90 (called unconditionally). All verified on first attempt except SetpointSmoother.

**SetpointSmoother verification failure:** `lpfilter_c` was called with 7 arguments instead of 9. The LPFilter callee bridge includes `has_InitialValue` and `InitialValue` trailing parameters for Fortran OPTIONAL args. The Fortran source at the SetpointSmoother call site doesn't use these OPTIONAL args, so they weren't obvious from reading the source alone.

**Lesson:** Always use `vit translate` to generate scaffolds. The translation prompt includes correct callee `_c` signatures from VIT's bridge generation, which would have shown the 9-arg signature immediately. Added explicit "always use vit translate" guidance to CLAUDE.md. Applied same fix to ComputeVariablesSetpoints (also calls LPFilter) before verifying it.

**Scenario 9 functions (3):** RefSpeedExclusion (TRA_Mode>0), Shutdown (SD_Mode>0), Startup (SU_Mode>0). These required a new simulation scenario.

**Scenario 9 creation:** Added `run_scenario_9()` to `vit_sim.py` with SU_Mode=1, SD_Mode=1, TRA_Mode=1 and appropriate parameters. Used the standard `ROSCO_sim.Sim` approach (not manual loop) since all three functions are called every timestep when their mode flags are set.

**Scenario 9 extraction failure — zero state files:** All three extractions produced zero state files. The simulation ran but no call sites were reached. Investigation revealed the root cause was **not** the gated call sites (even WindSpeedEstimator at line 109, called unconditionally, failed with Scenario 9).

**Root cause:** ROSCO's input validation rejected `SD_MaxPitchRate = 0.2 rad/s` because it exceeded `PC_MaxRat = 0.1745 rad/s`. The validation set `aviFAIL < 0`, which caused the controller to abort on first call. The IF condition at DISCON.F90:99 (`ErrVar%aviFAIL >= 0`) failed, so no code past line 99 executed — including all the call sites we wanted to instrument.

**Fix:** Reduced `SD_MaxPitchRate` from `'0.1 0.2'` to `'0.05 0.1'` (both below PC_MaxRat). All three extractions then succeeded: RefSpeedExclusion (22 cases), Shutdown (21 cases), Startup (20 cases).

**Translation notes:**
- Startup accesses ALLOCATABLE arrays from ControlParameters view (`SU_LoadStages`, `SU_LoadRampDuration`, `SU_LoadHoldDuration`) with computed indices. Fortran 1-based → C 0-based indexing required careful mapping: `SU_LoadRampDuration(SU_Stage-1)` → C `SU_LoadRampDuration[SU_Stage-2]`.
- Shutdown has two methods (time-based and pitch-based) with array-indexed stage parameters. Same indexing care needed.
- RefSpeedExclusion calls `ratelimit_c` with 9 args (including OPTIONAL `has_ResetValue`, `ResetValue`).

All three verified on first attempt after fixing the OPTIONAL param signatures.

### Tier 3 (8C): WindSpeedEstimator + Dependencies

**VIT 2D assumed-shape array support:** interp2d's `zData` parameter is `DIMENSION(:,:)` — the first rank-2 assumed-shape array in the project. VIT previously generated a single `n_<name>` size parameter for all assumed-shape arrays regardless of rank, which is wrong for 2D.

Changes made:
- `fortran_parser.py`: Added `array_rank` property to `FortranArg` (counts commas in `array_dims` + 1)
- `interface_gen.py`: Five functions updated to handle rank-2 arrays:
  - `build_c_params()`: Generate `n_<name>_rows` + `n_<name>_cols` instead of single `n_<name>`
  - `_build_interface_args()`: Same for BIND(C) Fortran interface
  - `_build_wrapper_call_args()`: Generate `SIZE(array, 1)`, `SIZE(array, 2)` instead of `SIZE(array)`
  - `_build_bridge_call_args()`: Use `RESHAPE(array(1:rows*cols), (/rows, cols/))` for 2D callee bridges
- `kernel_verify.py`: Fixed `-lstdc++` link order (append after objects, not before — gfortran requires libraries after the objects that reference them)

All 557 existing unit tests passed. Spot check: interp1d (rank-1 function) still verified 20/20.

**interp2d translation:** 172 lines of bilinear interpolation with boundary handling. Key challenge: Fortran `zData(:,j)` (column slice) is contiguous in column-major layout, but `zData(i,:)` (row slice) is strided. Solution: column slices passed as pointer directly (`&zData[j * n_rows]`), row slices copied to temp array via `new double[n_xData]`.

Initial verification failed with `undefined reference to 'operator new[]'` — the `-lstdc++` flag was placed before the `.o` files in the link command. Fixed the VIT Makefile generation to append `-lstdc++` at end of line. Verified 21/21.

**AeroDynTorque translation:** 39 lines, simple aerodynamic torque calculation. First function using PerformanceData view type (2D ALLOCATABLE fields `Cp_mat`, `Ct_mat`, `Cq_mat` exposed as flat column-major pointers with row/col counts). Calls `interp2d_c` with the new 2D signature. Verified 20/20 on first attempt.

**WindSpeedEstimator translation:** 222 lines, the most complex function in ROSCO. Three code paths:
- WE_Mode=0: Simple low-pass filter on hub height wind speed
- WE_Mode=1: Inversion and Invariance filter (calls AeroDynTorque)
- WE_Mode=2: Extended Kalman Filter with 3×3 matrix operations

EKF implementation required:
- WE struct access with column-major to row-major mapping: `Fortran P(i,j)` = `C P[j-1][i-1]`
- Inline 3×3 matrix multiply (MATMUL), transpose, and identity operations — all done with explicit loops since matrices are tiny
- 5 callee bridges: LPFilter (with OPTIONAL InitialValue), saturate, interp1d, interp2d, AeroDynTorque
- `ieee_is_nan()` → `std::isnan()`
- `EPSILON(1.0_DbKi)` → `std::numeric_limits<double>::epsilon()`
- Warning message via `fprintf(stderr, ...)` matching Fortran PRINT behavior

Key design decision: inlined `identity(3)` as `(i == j ? 1.0 : 0.0)` instead of calling `identity_c()`. This avoids the complexity of array-valued return callee bridges. VIT verification only checks the target function's input/output state, not internal call paths, so inlining is semantically equivalent.

**Verified 21/21 on first attempt.** All matrix operations, EKF updates, and callee bridge calls produce bit-identical results to the Fortran original.

## Key Lessons

1. **ROSCO input validation can silently abort the controller.** A parameter constraint violation (`SD_MaxPitchRate > PC_MaxRat`) set `aviFAIL < 0` on the first call, preventing ALL subsequent code from executing. This manifests as "zero state files" during extraction with no obvious error. Always test new scenarios with the uninstrumented library first and check for ROSCO validation warnings.

2. **`vit verify` requires clean source.** The callee bridge detection scans the ROSCO source directory. Integrated source (with `_c()` wrappers) breaks detection because the function signatures are modified. This dependency was implicit until Phase 8A exposed it.

3. **Always use `vit translate` for scaffolds.** The translation prompt includes correct callee `_c` signatures with OPTIONAL parameter handling. Writing translations manually from Fortran source misses trailing optional args (e.g., LPFilter's `has_InitialValue`/`InitialValue`).

4. **gfortran link order matters.** Libraries (`-lstdc++`) must come after the object files that reference them. The previous VIT code placed `-lstdc++` before `.o` files, which only surfaced when interp2d used C++ `new[]`/`delete[]`.

5. **Column-major to row-major mapping for nested struct arrays.** The VIT-generated comment `Fortran P(i,j) maps to C P[j-1][i-1]` was critical for the EKF implementation. Using macros (`#define WE_P(i,j) LocalVar->WE.P[(j)-1][(i)-1]`) kept the C++ visually close to the Fortran, reducing translation errors.
