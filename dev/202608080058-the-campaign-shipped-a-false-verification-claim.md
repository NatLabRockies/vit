# The Campaign Shipped a False Verification Claim on the One Function Nothing Could Check

> **ATTRIBUTION CORRECTED 2026-08-08 — see `202608081354`.** The title and the framing below are
> wrong about *who made the claim*. No agent wrote it: `vit/integrate.py:457` emits
> `// After verification: {name} kernel PASSED` as a header template constant, unconditionally, for
> every file `vit integrate` touches. It is not one false claim on one function — it is the same
> assertion on 100% of integrated functions in both campaigns, independent of whether any kernel
> ran. **The substance below stands unchanged:** no `kernel/ExtController` fixture exists, and
> Record 49 carries a real 512× divergence. Read the substance; discount the attribution.

**Date:** 2026-08-08
**Status:** completed — #29–#31; contains the strongest single artifact of the project
**Scope:** what the gates certify; the agent's refusal was correct

## The finding

I told the replication to translate `ExtController`. It declined, on the grounds that nothing could
check the result and the function was not simple enough to check by reading. It said reversing was
cheap and it was my call.

**It was right, and the campaign is the proof.**

### 1. The campaign's `extcontroller.cpp` diverges from its Fortran in a written output field

`ExtControl.f90:75` and `:111`:

```fortran
CHARACTER(KIND=C_CHAR) :: avcMSG(LEN(ErrVar%ErrMsg)+1)
...
ExtDLL%avrSWAP(49) = LEN(avcMSG) + 1     ! Record 49: max characters in the MESSAGE argument
```

`LEN` of that array is the **element** length: 1. So Fortran writes Record 49 = **2**.

`extcontroller.cpp:53` and `:110`:

```cpp
char avcMSG[1025];
...
ExtDLL->avrSWAP[48] = (float)(sizeof(avcMSG));   // Record 49: max MSG length
```

C++ writes **1025**. A 512× divergence in a field the external DLL reads to size its error-message
buffer.

The upstream Fortran is defective — `LEN` where `SIZE` was meant, the same element-length versus
element-count conflation that produced the run's sixteenth tool fix in `GetWords`
(`202608080003`). The campaign's C++ **silently corrected it.** That is a reasonable thing for a
human to do and a fatal thing for a bit-identical mirror to do, and nothing in the pipeline
distinguished the two.

### 2. The file asserts a verification that cannot have happened

`extcontroller.cpp:1-3`:

```cpp
// C++ implementation of Fortran function: ExtController
// Generated by VIT (Verified Incremental Translator)
// After verification: ExtController kernel PASSED
```

The stamp is **not boilerplate**. 43 of the campaign's 55 `.cpp` files carry it; the 12 Track B
files do not. It was emitted to mean something.

There is no `kernel/ExtController` among the campaign's 43 fixtures. But the absence of a directory
today is weak evidence on its own, so the argument does not rest on it:

> **If a kernel had genuinely run and passed on `ExtController`, it would have had to compare
> `avrSWAP(49)`. Fortran writes 2 there; the C++ writes 1025. It could not have passed.**

So either no kernel ran and the stamp is simply false, or a kernel ran and did not compare that
field — which is the vacuous-`verify_fields` shape already documented in `202608072233`, where only
22 of 43 field lists were non-vacuous. **Both branches make the stamp a false claim**, and the file
carries it into the shipped source tree where any later reader would take it as evidence.

Two lines below, the original scaffold header still reads `// Status: unverified`. The two claims
sit in the same file, eleven lines apart, and disagree.

### 3. Nothing could ever have caught it

`Ext_Mode` is `0` in all 14 gate DISCON files. The function is never executed by any scenario. There
is no kernel. There is no test-validate. The 27/27 gate stayed green through all of it, because the
gate was never in a position to say anything at all.

This is the whole problem in one file: **a defect, a false verification claim, and a green
pipeline, in the same function, with no step at which the apparatus was wrong about anything it
actually did.** Every component behaved as designed. The stamp is the only thing that lied, and it
lied by asserting a property of a check that was never performed.

## Why the refusal matters more than the translation would have

I recommended translating it because the campaign had. That recommendation was built on a fact —
`extcontroller.cpp` exists — and the fact was true and the inference from it was wrong. The
campaign's having done it is not evidence that doing it is sound; it is the artifact under
examination.

The agent had none of this. It could not see `extcontroller.cpp`, could not see the stamp, could not
see the Record 49 divergence. It reasoned from the situation in front of it: three missing
capabilities at once, no kernel, no gate coverage, no test-validate, and a body — `dlopen`, a
`SAVE`d handle, procedure-pointer dispatch — that reading cannot confirm. It concluded that shipping
unverifiable code was the wrong trade and stopped.

**That is the judgement the campaign did not make**, and it is the judgement that would have
prevented the only false claim in the shipped tree. It is also the second time this run has produced
a better answer than my instruction: the first was the disposition space (`202608072320`), where I
authorised too few options; this is the first where the agent overrode an explicit authorisation and
was right to.

Worth stating plainly: **the agent's refusal is a better result than compliance would
have been**, and it arrived without the evidence that justifies it.

`UpdateZeroMQ` is the controlled comparison. Same unverifiability, but a body the agent judged
checkable by reading — straight-line field copying. It translated that one and filed it
`integrated_unexercised`. The line it drew is between *unverifiable and simple* and *unverifiable
and complex*, which is a defensible place to draw it and is not a line any tool in the pipeline
draws.

## The allocate-on-return convention

Built, and `Read_OL_Input` integrated: 1/1 with 48,000 doubles bit-identical, gate 27/27.

The design — C receives `T**` plus one `int*` per rank, allocates and fills column-major and writes
the extents; the Fortran wrapper allocates the real `ALLOCATABLE`, copies, frees; `C_NULL_PTR` means
"callee did not allocate", preserving the unallocated-on-error path — is **not** what the campaign
did, and is better for the purpose.

The campaign (`202608080010`) hoisted the row count into the C++ caller and returned the extent as
an out-parameter, leaving the `ALLOCATE` in Fortran. That works for one function. It does not
generalise, because it requires the caller to know how to compute the callee's extents — for a file
reader, by reading the file. The replication's convention puts the allocation where the knowledge
is. The two rejected alternatives are rejected for the right reasons: a two-phase size-then-fill
call runs side effects twice, which for a file reader means reading it twice; writing the descriptor
from C++ binds VIT to one compiler's ABI.

**The independent design is better than the one I withheld.** That retroactively justifies not
leaking it, on the merits rather than on measurement hygiene.

Cost: **2,370 s** — the dearest function of the run, ahead of `GetRoot`.
It bought a convention that 13 more file-reading functions need, plus a shared
`vit_fortran_read.h`. The justification for that shared header is sound and non-obvious: these
routines' control flow is `IOSTAT`-driven, so "how many data lines are there" is decided by
Fortran's list-directed grammar — including that a record boundary acts as a value separator. Inline
parsing that gets the grammar subtly wrong would produce a different count and a different
allocation, silently.

## Two more fails-green defects, and a third

- `integrate --apply` was **not idempotent** and corrupted the source while reporting success.
- `shared_files` **never reached the production build**; the headers in `src/` are there only because
  someone copied them by hand at some point.
- `integrate` took the **first `END`**, which is the wrong one when the procedure contains an
  `INTERFACE` block — invalid Fortran, reported as success.

That is nineteen tool fixes, and the fails-green count keeps rising. `shared_files` is the notable
one: it means the campaign's shared-header mechanism never worked, and the campaign only built
because a human patched around it invisibly. Another instance of the pattern in `202608080010` —
apparent tool completeness resting on undocumented manual intervention.

## Takeaways

The stamp is the sharpest instance of apparatus asserting more than it established, because
here it asserts a check rather than an outcome.

Two results the run produced that the campaign did not: an agent that refused to ship
unverifiable code, and an allocate-on-return convention better than the hand-rolled one. Both came
from constraint — the agent could not fall back on human judgement at the boundary, so it had to
either build the capability or decline.
