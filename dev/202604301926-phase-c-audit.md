# Phase C Code Audit
**Date:** 2026-04-30
**Status:** completed
**Scope:** All 10 DBEMT C++ translations + VIT infrastructure changes

## Audit Scope

Full audit of all DBEMT translations (10 .cpp files), VIT infrastructure changes (interface_gen.py, kernel_verify.py), shared headers (vit_nwtc.h/.cpp, vit_fortran_intrinsics.h), production bridge (vit_bridge_extrapinterp.f90), and integration scripts (integrate_all.sh, reset_to_clean.sh). ## Real Issues Found and Fixed

### 1. ExtrapInterp Bridge CHARACTER Buffer Truncation

**File:** `modules/aerodyn/src/vit_bridge_extrapinterp.f90`, lines 18 and 23

The production bridge used `CHARACTER(1024)` for the local ErrMsg buffer, but ErrMsgLen is 8196. The copy loop also capped at 1024. Any error message exceeding 1024 characters from `DBEMT_ElementInputType_ExtrapInterp` would be silently truncated, leaving stale data in the C++ caller's buffer past position 1024.

**Fix:** Changed to `CHARACTER(8196)` and `MIN(LEN_TRIM(local_ErrMsg), 8196)`.

### 2. Repair Loop Safety Cap

**File:** `vit/vit/kernel_verify.py`, `_repair_kernel_build`

The `while True` loop (from the earlier idempotency fix) relied entirely on fix function idempotency to terminate. If a fix function had a regex bug that prevented its idempotency guard from matching, the loop would hang indefinitely.

**Fix:** Added `max_iterations=100` defense-in-depth cap. Normal kernels need ≤6 iterations. The cap only fires if there's a bug in a fix function — it's a safety net, not a design constraint.

## False Positives Evaluated and Dismissed

The audit agents flagged many patterns that are intentional Fortran-to-C++ translation conventions:

| Flag | Why It's Not an Issue |
|------|----------------------|
| Physics constants (0.39, 0.26, 1.3, 1.1, 100.0) | Match Fortran source exactly. Naming them would obscure the 1:1 correspondence that makes translation verification possible. |
| `for (k=0; k<2; k++)` hardcoded dimension | Matches `vind[2]` struct field and Fortran `do indx=1,2`. A named constant would add indirection without benefit. |
| Column-major indexing `(j-1)*n_rows + (i-1)` | Standard pattern, consistent across all 10 files. An accessor function would obscure direct array access. |
| 1-based loop indices in AllNodes | Intentional — callees expect 1-based i,j for their own indexing. |
| `extern "C"` declarations per file | Design pattern — each translation is self-contained, not coupled via shared headers. |
| "Unused" parameters (t, p, m in CalcOutput) | Match Fortran signature. Removing would break the BIND(C) interface. |
| RK4/AB4/ABM4 numerical coefficients | Mathematical constants of the integration methods. Hardcoded in Fortran too. |
| 2D fixed-size view arrays not supported | No current use case. Extend when encountered (YAGNI). |
| `fortran_intrinsics.h` double assumption | Works for all OpenFAST types (ReKi = REAL(8) = double). Template improvement is future work if non-double use cases arise. |
| CHARACTER(*) default 4096 "unused" | Actually used — caller applies default via `dict.get(var_name, 4096)`. Agent misread the code. |
