# The Verification Stamp Is Emitted Unconditionally by the Tool

**Date:** 2026-08-08
**Status:** completed — defect located; **correction to `202608080058`'s attribution**
**Scope:** VIT tooling defect; claims-audit finding; deferred fix

## Placement

Same as the other replication notes: OpenFAST workspace, outside the replication's container mount
and outside the repository it commits to. **Do not merge into the ROSCO-workspace checkout until
the run has ended.**

## The finding

`vit/integrate.py:457`:

```python
lines.append(f"// C++ implementation of Fortran function: {sig.name}")
lines.append(f"// Generated by VIT (Verified Incremental Translator)")
lines.append(f"// After verification: {sig.name} kernel PASSED")
```

**It is a header template constant.** Emitted unconditionally, for every file `vit integrate`
touches, beside `// Generated by VIT`. No verification state is consulted — not the kernel result,
not whether a kernel fixture exists, not which method was used.

So every integrated file in every campaign asserts kernel verification, and the assertion is
independent of whether any kernel ever ran.

## How it was found

The first check written for the outer-loop repository (`checks/claims.py`, milestone M1) resolves
every verification claim in a tree against the artifact it names. It reproduced its known answer on
the original campaign — 43 claims across 55 files, exactly one unresolved, `extcontroller.cpp:3` —
and then returned **three** on the replication where I had predicted zero:

| Function | Stamp says | Actually verified by |
|---|---|---|
| `PIIController` | kernel PASSED | 6/6 `vit test-validate` |
| `UpdateZeroMQ` | kernel PASSED | nothing — `integrated_unexercised` |
| `ChkParseData` | kernel PASSED | nothing — `integrated_unexercised` |

Investigating the discrepancy rather than adjusting the expectation found the line above. The check
found a defect on its first run past its known answer, which is the best possible outcome for a first
milestone and the reason M1 was chosen to go first.

## The correction to `202608080058`

That note is titled **"The Campaign Shipped a False Verification Claim."** Its attribution is wrong
and the title is wrong.

- **Wrong:** an agent wrote a claim of kernel verification for a function it had not kernel-verified.
- **Right:** the toolchain writes that claim into every integrated file, unconditionally. No agent
  authored it.

**This makes the defect worse, not better.** It is not one bad claim in one campaign; it is the
manufactured appearance of kernel verification across **100% of integrated functions in both
campaigns** — 43 in the original, 46 and counting in the replication. Every one of them reads like a
record of an event.

**The substantive `ExtController` finding is unaffected.** No `kernel/ExtController` fixture exists,
and Record 49 carries a real 512× divergence — the C++ writes `sizeof(avcMSG)` = 1025 where the
Fortran writes `LEN(avcMSG)+1` = 2. That function is wrong and unverified, and the stamp sat on top
of it. What changes is where the defect lives: in the toolchain, not in a report.

This is my eleventh caught error, and the first caught by an instrument rather than by a person.

## Why it belongs in the failure catalogue

It is the purest instance of the project's central pattern yet found, because the *mechanism* is
explicit rather than emergent:

> A record of verification, emitted by the step that runs **after** verification, containing no
> information about verification.

Placement is what sells it. `vit integrate` runs at step 5 of the 7-step workflow, immediately after
`vit verify`. A line written there, phrased in the past tense, reads as the outcome of the step that
just completed. It is a constant.

Compare failure #1 — a gate printing `PASS: 27/27` while comparing nothing. Same shape, and this one
is shorter: there, an apparatus ran and established nothing; here, no apparatus runs at all and the
sentence is simply asserted.

## The fix — deferred, and the reasoning

**One line, zero functional impact.** Two options:

1. **Emit conditionally** — write the stamp only when a kernel fixture with state files exists for
   this function, and otherwise write nothing.
2. **Emit the truth** — record the method and the result actually obtained: `// Verified: 6/6
   vit test-validate` / `// Verified: 21/21 kernel` / `// NOT VERIFIED: integrated_unexercised`.

**Option 2 is better** and is what the project's own evidence-strength argument calls for
(`202608072158`: a 20/20 on a non-discriminating input and a 20/20 on a rich one print identically).
It requires `vit integrate` to have access to the verification record, which it may not today —
worth checking before committing to it. Option 1 is available unconditionally and removes the false
assertion immediately.

**Deferred rather than relayed.** It touches VIT mid-run, and:

- It blocks nothing. No function's verification depends on it.
- The information is already recorded correctly elsewhere — `STATUS.md`, `DECISIONS.md`, and the
  commit messages all name the real method for all three flagged functions. The stamp is the only
  place that lies.
- Changing tooling mid-run has a comparability cost, and this defect has none of the urgency that
  justified the two mid-run fixes that were made.

Recorded as deferred item 11.

## What it says about the claims audit

The check is worth its forty lines. It reproduced a known answer on one tree, found an unknown defect
on a second, and the defect it found reframes an earlier finding. It also demonstrates the design
rule it was built to enforce — **the claim and the artifact are both in the repository, so the
cross-reference is mechanical** — and that the right response to an unexpected result is to
investigate it rather than to relax the expectation.

This reframes the `ExtController` finding. "One function carried a false stamp" is
an anecdote; "the translator stamps an unearned verification claim into every file it emits, in the
step immediately after verification, and it survived a completed campaign and 46 functions of a
replication" is the finding. It is also the cleanest available example of apparatus manufacturing
evidence, because there is no apparatus — only a format string.

It was found by an automated claims audit
rather than by review, which is the argument for building one.
